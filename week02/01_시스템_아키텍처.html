1. 한눈에 보기

MechDog 4대가 공장·창고 통로를 한 방향으로 순찰하며 통로 장애물, 안전모 착용, 화재를 살핀다. 이상을 찾으면 사진과 구역을 관제 대시보드에 띄워 사람이 조치하고, 화재가 확정되면 로봇들이 갈림길에 서서 LED로 비상구 방향을 가리킨다.

로봇층 · MechDog 제어 보드몸으로 하는 일. 걷기, 선 따라가기, 초음파로 멈추기, LED 표시
엣지층 · 라즈베리 파이 5눈으로 하는 일. 로봇마다 1대. 카메라·온도로 판단하고 결과와 사진만 보냄
관제층 · 노트북 서버 + 대시보드여러 대를 엮는 일. 위치, 교차 확인, 교대·출동·대피 지휘, 관리자 화면

원칙: 판단은 가장 가까운 곳에서 한다. 멈추는 판단은 보드가, 보고 아는 판단은 Pi가, 여러 대를 엮는 판단은 서버가 맡는다. 서버가 끊겨도 로봇은 순찰을 계속한다.

3. 판단을 어디서 하나

층반응판단하는 것위가 끊겼을 때
보드즉시선 따라가기, 초음파 정지·재개, 마커 색 읽기, 이동 명령 시간 제한Pi가 2초 넘게 조용하면 멈추고 LED에 오류 표시
Pi 50.3~0.5초안전모 착용, 불꽃, 사람(장애물에서 빼기), 화재 의심, 사진 촬영서버가 끊겨도 순찰 계속. 이벤트는 쌓아 두었다가 다시 붙으면 보냄
서버1~2초구역 위치, 화재 확정(교차 확인), 충전 교대, 출동, 대피 배정, 합류점 우선권—

서버와 끊긴 동안에도 합류점에서는 미션맵 동선 규칙의 우선권대로 양보한다. 순찰 경로가 모두 한 방향이라 합류점만 지키면 마주치지 않는다.

4. 통신

아래 약속은 팀 저장소의 common/protocol.py(코드)와 docs/protocol.md(표)에 같은 내용으로 있다.

4-1. 보드 ↔ Pi 5 (USB 시리얼)

보드 USB와 Pi USB-A를 케이블 하나로 잇는다. 공식 예제(Hiwonder.UART, PC 시리얼 제어)와 동작 시험 도구가 쓰는 CMD|…|$ 형식을 그대로 쓰고, 보드 포트 1~3은 센서 · LED · MP3에 남긴다. Pi는 포트를 열 때 보드가 다시 켜지지 않게 DTR · RTS를 끈 채 연다. USB가 안 되면 같은 명령을 BLE로 주고받는다(시험 도구 방식).

방향메시지뜻
Pi → 보드F|보폭|각도|ms · U|보폭|정지cm|재개cm|ms선 따라가기 · 초음파 정지 걷기
Pi → 보드S · P · L|모드|값정지 · 기본 자세 · LED 표시
Pi → 보드A|번호|볼륨음성 재생 (MP3 모듈 트랙 번호, 볼륨 0~30)
Pi → 보드T|간격ms|채널,…측정값 보내기 시작 (bat · sonar · line · color)
Pi → 보드V보드 프로그램 버전 · 지원 명령 묻기
보드 → PiCMD|D|t|값…|$ · CMD|E|t|채널|값|$측정값 · 이벤트 (막힘 정지 stop, 재개 resume, 마커 색 color, 이동 끝 done)

머리 카메라 → Pi 5 (USB): XIAO가 640×480 JPEG를 초당 15장쯤(약 450KB/s) 계속 보낸다. 로봇마다 선이 따로라 4대가 서로 영향을 주지 않고, Wi-Fi는 상태·이벤트·사진에만 쓴다. Pi는 밀린 장을 버리고 가장 최근 장만 추론한다.

4-2. Pi 5 ↔ 서버 (Wi-Fi · MQTT)

토픽방향 · 주기내용
potent/{로봇}/statePi → 서버, 1초마다지난 마커, 상태, 배터리, 초음파 거리, 온도
potent/{로봇}/eventPi → 서버, 생길 때종류(obstacle · floor_object · helmet · heat · flame), 값, 신뢰도, 사진 주소
potent/{로봇}/cmd서버 → Pipatrol · stop · resume · go(구역) · wait · dock · guide(화살표)
potent/mode서버 → 전체normal(평상시) · evacuate(화재 대피)
사진Pi → 서버, HTTPPOST /photos로 올리고 받은 주소를 이벤트에 넣음
// potent/B/event 예시
{ "type": "obstacle", "marker": 14, "sonar_cm": 12,
  "person": false, "photo": "/photos/B_1117_103512.jpg", "ts": 1763343312 }

4-3. 서버 ↔ 대시보드

서버가 상태·이벤트를 WebSocket으로 밀어 주고, 관리자의 확인·해제는 HTTP로 받는다. 이벤트는 2초 안에 화면에 뜨는 것이 목표다.

업데이트: 로봇을 분해하지 않고 노트북에서 Wi-Fi로 4대를 한 번에 올린다. 보드는 Pi에 USB로 늘 꽂혀 있어 Pi를 거쳐 올린다. 업데이트는 로봇이 충전 · 대기 중일 때만 한다.

대상방법지킬 것
Pi 프로그램 · AI 모델노트북 스크립트로 4대에 SSH → git pull → 서비스 재시작. 모델은 models/에 버전을 붙여 넣는다상태 보고에 git 커밋을 넣어 대시보드에서 4대의 버전을 본다
보드 프로그램Pi가 USB 시리얼로 main.py를 올리고(mpremote) 보드를 다시 켠다. 이전 파일은 main_prev.py로 남긴다보드는 V 명령으로 버전을 답한다
Pi OS · 보드 기본 펌웨어거의 바꾸지 않는다. Pi는 같은 이미지의 microSD로 바꿔 끼우고, 보드 펌웨어는 Pi에서 esptool로 굽는다캐리어가 microSD 슬롯을 막지 않는다
바닥 카메라 · XIAO 펌웨어바닥 카메라는 PC에서 모듈 USB-C로, XIAO는 Pi에서 esptool로 굽는다머리 아래 모듈의 USB-C를 브래킷이 막지 않는다

가짜 로봇: 서버와 대시보드는 로봇 없이 fake_robots.py로 먼저 만든다. MQTT 메시지 형식(4-2)이 지켜지면 로봇·Pi 쪽과 따로 개발해도 나중에 그대로 붙는다.
